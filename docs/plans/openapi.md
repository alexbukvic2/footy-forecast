# Plan: OpenAPI Integration

**File:** `docs/plans/openapi.md`
**Date:** 2026-05-24
**Status:** Draft

---

## 1. Goal

Introduce OpenAPI 3.1 as the canonical API contract for footy-forecast, backed by `oapi-codegen` for compile-time type generation, so that the spec is the single source of truth for all HTTP routes and cannot drift from the Go types.

---

## 2. Out of Scope

- Runtime request validation from the spec (can be layered on later with oapi-codegen middleware or kin-openapi).
- Generating the Postman collection from the spec — Postman is kept as a test runner and maintained in parallel.
- Refactoring existing handler request/response structs to use generated types (existing structs stay; new routes use generated types from day one).

---

## 3. Data Model Changes

None. This is a tooling and documentation change only.

---

## 4. API Contract

Not applicable — this plan establishes the contract infrastructure. The output of Phase 1 *is* the contract document (`docs/openapi.yaml`).

---

## 5. Tooling Decision

**`oapi-codegen`** (`github.com/oapi-codegen/oapi-codegen/v2`) is added as a **build-time tool only** — no runtime dependency.

Justification over alternatives:

| Option | Verdict |
|--------|---------|
| `swaggo/swag` (annotations → spec) | Rejected. Noisy comments couple docs to code. Violates spec-first intent. |
| Handwritten types with no codegen | Rejected. Types drift from spec silently; no compile-time enforcement. |
| Runtime validation only (kin-openapi) | Deferred. Valuable, but bigger change. Orthogonal to this plan. |
| `oapi-codegen` (spec → types) | Accepted. Build-time only, zero runtime overhead, generates idiomatic `net/http`-compatible types, version-pinned via `go.mod tool` directive. |

`oapi-codegen` is added under the `tool` directive in `go.mod` (same pattern as `goose` and `sqlc`).

## 6. File Layout

```
docs/
  openapi.yaml                          # Canonical spec (OpenAPI 3.1) — edit this
internal/
  server/
    oapi/
      doc.go                            # go:generate directive
      models.gen.go                     # Generated — DO NOT EDIT
      oapi-codegen.yaml                 # Codegen config
Makefile                                # +generate target
.github/workflows/ci.yml               # +drift check
```

`models.gen.go` carries a `// Code generated by oapi-codegen. DO NOT EDIT.` header and is committed to the repository, the same convention as `internal/repository/dbgen/`.

## 7. Phase 1 — Write the Spec (Retrofit)

Write `docs/openapi.yaml` covering all 18 existing routes.

### 7a. Top-level metadata

```yaml
openapi: "3.1.0"
info:
  title: footy-forecast API
  version: "0.1.0"
  description: >
    Football prediction game API. Predictions lock at kickoff;
    scoring is deterministic and updated in near real-time.
servers:
  - url: http://localhost:8080
    description: Local development
  - url: https://<prod-domain>
    description: Production
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
```

### 7b. Routes to document

| Method | Path | Auth | Notes |
|--------|------|------|-------|
| GET | `/health` | None | Liveness probe |
| GET | `/health/ready` | None | Readiness — checks DB |
| GET | `/tournaments` | None | List all |
| GET | `/tournaments/{id}` | None | By UUID |
| POST | `/tournaments` | Bearer | Create |
| GET | `/users/me` | Bearer | Current user profile |
| GET | `/leagues` | Bearer | User's leagues |
| GET | `/leagues/{id}` | Bearer | League + members |
| POST | `/leagues` | Bearer | Create |
| POST | `/leagues/join` | Bearer | Join via invite code |
| PATCH | `/leagues/{id}` | Bearer | Update name |
| DELETE | `/leagues/{id}` | Bearer | Delete |
| POST | `/leagues/{id}/code` | Bearer | Regenerate invite code |
| DELETE | `/leagues/{id}/members/{userId}` | Bearer | Remove member |
| GET | `/tournaments/{tournament_id}/players/search` | Bearer | `?q=` search |
| GET | `/player-handicaps/{player_id}/{category}` | Bearer | |
| GET | `/team-handicaps/{team_id}/{category}` | Bearer | |

Public routes carry `security: []` (explicit empty array overrides the global default). Protected routes carry `security: [{bearerAuth: []}]`.

### 7c. Reusable components (`components/schemas`)

Define these once and `$ref` them throughout the spec:

| Schema | Shape |
|--------|-------|
| `ErrorResponse` | `{error: string}` |
| `Tournament` | id, slug, name, … |
| `League` | id, name, invite_code, … |
| `LeagueMember` | user_id, display_name, … |
| `User` | id, display_name, email, … |
| `Player` | id, name, team_name, team_logo, handicaps |
| `PlayerHandicap` | `{points: integer}` |
| `TeamHandicap` | `{points: integer}` |
| `PlayerHandicapCategory` | enum: `group_top_scorer`, `total_top_scorer` |
| `TeamHandicapCategory` | enum: `group_winner`, `playoff`, `semifinalist`, `winner` |

Each schema must include at least one `example`.

### 7d. Standard error responses

Every route must document these responses (ref `ErrorResponse`):

| Status | Condition |
|--------|-----------|
| 400 | Malformed input (invalid UUID, unknown enum value, etc.) |
| 401 | Missing or invalid JWT (protected routes only) |
| 404 | Resource not found |
| 500 | Unexpected server error |

## 8. Phase 2 — oapi-codegen Integration

### 8a. Codegen config (`internal/server/oapi/oapi-codegen.yaml`)

Generate models only — no server stubs. This is the least-invasive option for a retrofit: existing handlers keep their own routing but can reference the generated types.

```yaml
package: oapi
output: models.gen.go
generate:
  models: true
  strict-server: false
  chi-server: false
  embedded-spec: false
```

### 8b. `go:generate` directive (`internal/server/oapi/doc.go`)

```go
//go:generate oapi-codegen -config oapi-codegen.yaml ../../../docs/openapi.yaml
package oapi
```

### 8c. Makefile

Add a `generate` target:

```makefile
generate:
	go generate ./...
```

Also add `generate` as a dependency of any target that compiles the binary, so it is never silently skipped.

### 8d. `go.mod`

Add under the `tool` directive:

```
github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen
```

Run `go get -tool github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen`, then `go mod tidy`.

### 8e. CI drift check

In `.github/workflows/ci.yml`, after `make generate`, add:

```yaml
- name: Check generated files are up to date
  run: git diff --exit-code internal/server/oapi/
```

This fails the build if someone updates `docs/openapi.yaml` without regenerating `models.gen.go`.

## 9. Phase 3 — Public Spec Endpoint, Swagger UI, and Mobile SDK

### 9a. `GET /openapi.json` — unauthenticated

Serve the OpenAPI spec as JSON so that automated tooling (mobile SDK generation,
third-party integrations) can consume it without authentication.

**Implementation approach — no new runtime dependencies:**

1. As part of `make generate`, a small conversion step converts `docs/openapi.yaml`
   to `docs/openapi.json`. The implementer can use `yq` (if available) or write
   a minimal `cmd/spec-gen/main.go` that reads the YAML and writes JSON using
   `gopkg.in/yaml.v3` + `encoding/json`. The JSON file is committed to the
   repository alongside the YAML.
2. Embed `docs/openapi.json` in the binary with `//go:embed`:
   ```go
   //go:embed ../../../docs/openapi.json
   var specJSON []byte
   ```
3. Register the route in the router — no auth middleware:
   ```
   GET /openapi.json  →  handler writes specJSON with Content-Type: application/json
   ```

This endpoint must be listed in `docs/openapi.yaml` itself (self-documenting),
under a `paths` entry with `security: []`.

### 9b. `GET /docs` — Swagger UI (unauthenticated)

Serve a minimal HTML page that loads Swagger UI from CDN and points it at
`/openapi.json`. No new runtime dependency — the HTML is a string constant
or `go:embed`-ed file.

```html
<!DOCTYPE html>
<html>
<head>
  <title>footy-forecast API</title>
  <link rel="stylesheet" href="https://unpkg.com/swagger-ui-dist/swagger-ui.css">
</head>
<body>
  <div id="swagger-ui"></div>
  <script src="https://unpkg.com/swagger-ui-dist/swagger-ui-bundle.js"></script>
  <script>
    SwaggerUIBundle({ url: "/openapi.json", dom_id: "#swagger-ui" });
  </script>
</body>
</html>
```

Register in the router without auth middleware:
```
GET /docs  →  handler writes the Swagger UI HTML with Content-Type: text/html
```

Add this route to the spec as well with `security: []`.

### 9c. Mobile SDK generation

The mobile client (React Native / TypeScript) runs:

```bash
npm run gen:api   # hits GET /openapi.json and generates a typed client
```

No server-side work beyond the `/openapi.json` endpoint. The mobile repo is
responsible for its own codegen tooling (e.g. `openapi-typescript-codegen`,
`orval`, or similar). Document the endpoint URL in the mobile project's README.

The spec must be kept accurate enough to be useful for codegen — all request and
response schemas must have explicit types (no `{}` or `any`).

## 10. Phase 4 — Spec-First Workflow (New Routes)

Once Phases 1–3 are in place, the workflow for every new route is:

1. **Plan** documents the endpoint in the "API Contract" section (see `.claude/agents/planner.md`).
2. **Implementer** adds the endpoint to `docs/openapi.yaml`, runs `make generate` (regenerates both `models.gen.go` and `docs/openapi.json`), then implements the handler using the generated types.
3. **Reviewer** checks that spec, generated types, handler, and Postman request are all consistent.

If there is ever a conflict between the spec and Postman, the spec wins.

## 12. Edge Cases

| Scenario | Handling |
|----------|----------|
| `openapi.yaml` and `openapi.json` diverge | CI drift check (`git diff --exit-code docs/openapi.json`) fails the build |
| `openapi.yaml` and `models.gen.go` diverge | CI drift check (`git diff --exit-code internal/server/oapi/`) fails the build |
| New enum value added to domain | Update spec + run `make generate` before writing any handler code |
| Route removed | Delete from spec, run `make generate`, delete handler and Postman request |
| Breaking change to response shape | Bump `info.version` in spec; call out in plan and PR description |
| Mobile client calls `/openapi.json` before spec is accurate | Spec accuracy is an acceptance criterion; inaccurate schemas produce broken SDK output |
| `oapi-codegen` version upgrade changes generated output | Re-run `make generate`, commit the diff; CI enforces it going forward |

## 13. Test Plan

No new unit or integration tests are introduced by this plan — it is tooling infrastructure. Correctness is enforced by:

- **CI drift check**: both `docs/openapi.json` and `models.gen.go` are always in sync with `docs/openapi.yaml`.
- **Compiler**: handler types referencing generated models break at compile time if the spec changes incompatibly.
- **Existing tests**: unchanged; all must continue to pass after `make generate`.

The two new HTTP handlers (`GET /openapi.json`, `GET /docs`) are simple static-response handlers. Each needs:
- One happy-path test verifying `Content-Type` and a non-empty body.
- No error-path tests (they cannot fail; they serve embedded bytes).

## 14. Acceptance Criteria

- [ ] `docs/openapi.yaml` documents all 18 existing routes plus `/openapi.json` and `/docs`, with accurate schemas and at least one example per schema
- [ ] All error responses use `$ref: '#/components/schemas/ErrorResponse'`
- [ ] `make generate` runs without errors and produces both `docs/openapi.json` and `internal/server/oapi/models.gen.go`
- [ ] `GET /openapi.json` returns the full spec with `Content-Type: application/json`, no auth required
- [ ] `GET /docs` returns a Swagger UI page that loads the spec from `/openapi.json`, no auth required
- [ ] `make fmt && make lint && make test` all pass after generation
- [ ] CI drift check fails when spec is modified without regenerating (verify locally)
- [ ] Mobile client can point `npm run gen:api` at `GET /openapi.json` and generate a valid TypeScript client
